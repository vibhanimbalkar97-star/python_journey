# **SQL Clauses in PostgreSQL – Complete Beginner to Interview Notes**

Let's understand SQL clauses from absolute beginner to interview level, with practical examples, common mistakes, problems, and their solutions.

## **1. What are SQL Clauses?**

**SQL clauses are parts of an SQL statement that perform specific tasks when working with database data.**

For example, imagine an employee table:

| id | name  | age | salary | department |
| -- | ----- | --- | ------ | ---------- |
| 1  | Rahul | 25  | 30000  | IT         |
| 2  | Priya | 28  | 45000  | HR         |
| 3  | Amit  | 24  | 25000  | IT         |
| 4  | Neha  | 30  | 50000  | Finance    |
| 5  | Sneha | 26  | 35000  | HR         |

Suppose you want:

- Only employees from IT.
- Employees whose salary is above 30,000.
- Employees sorted by salary.
- Only the first three employees.

SQL clauses help us do all these operations.

**Hindi:** Clauses SQL query ke different parts hain. Har clause ka apna kaam hota hai, jaise data filter karna, sort karna, group karna.

## **2. Main SQL Clauses**

| Clause   | Purpose                  | Example                      |
| -------- | ------------------------ | ---------------------------- |
| SELECT   | Choose columns           | `SELECT name`                |
| FROM     | Choose table             | `FROM employees`             |
| WHERE    | Filter rows              | `WHERE age > 25`             |
| DISTINCT | Remove duplicate results | `SELECT DISTINCT department` |
| GROUP BY | Group similar values     | `GROUP BY department`        |
| HAVING   | Filter groups            | `HAVING COUNT(*) > 2`        |
| ORDER BY | Sort results             | `ORDER BY salary DESC`       |
| LIMIT    | Restrict returned rows   | `LIMIT 5`                    |
| OFFSET   | Skip rows                | `OFFSET 5`                   |

We'll understand each one.

# **3. SELECT Clause**

**What?**

SELECT is used to retrieve specific columns or expressions from a table.

**Why?**

To get only the information you need instead of fetching every column.

**Syntax:**

```
SELECT column1, column2
FROM table_name;
```

Example:

```
SELECT name, salary
FROM employees;
```

Output:

| name  | salary |
| ----- | ------ |
| Rahul | 30000  |
| Priya | 45000  |
| Amit  | 25000  |
| Neha  | 50000  |
| Sneha | 35000  |

### **Select all columns**

```
SELECT *
FROM employees;
```

`*` means all columns.

### **Select calculated values**

```
SELECT name, salary, salary * 12 AS annual_salary
FROM employees;
```

`AS` gives a temporary name (alias) to a result column.

### **Problems with SELECT**

**Problem 1: Using SELECT \***

```
SELECT * FROM employees;
```

Why can this be a problem?

- Fetches unnecessary columns.
- Can increase data transfer.
- Makes queries less clear.
- Can expose sensitive columns unintentionally.

**Solution:** Select only the required columns.

```
SELECT name, salary
FROM employees;
```

**Interview question:** Is SELECT a filtering clause?

No. SELECT chooses which columns or expressions to return. WHERE filters rows.

# **4. FROM Clause**

**What?**

FROM specifies which table or data source to retrieve data from.

**Syntax:**

```
SELECT columns
FROM table_name;
```

Example:

```
SELECT *
FROM employees;
```

Here, `employees` is the source table.

### **Using multiple tables**

```
SELECT employees.name, departments.department_name
FROM employees
JOIN departments
ON employees.department_id = departments.id;
```

FROM and JOIN together specify the data sources.

### **Common problem**

**Problem:** Using multiple tables without a proper join condition can produce a Cartesian product, creating many unexpected rows.

**Solution:** Use the correct JOIN condition.

# **5. WHERE Clause**

Very important for interviews

**What?**

WHERE filters individual rows based on a condition.

**Why?**

To retrieve only the records that match your requirements.

**Syntax:**

```
SELECT columns
FROM table_name
WHERE condition;
```

Example:

```
SELECT *
FROM employees
WHERE salary > 30000;
```

Output:

| id | name  | salary |
| -- | ----- | ------ |
| 2  | Priya | 45000  |
| 4  | Neha  | 50000  |
| 5  | Sneha | 35000  |

### **Important operators used with WHERE**

| Operator     | Purpose               | Example                                  |
| ------------ | --------------------- | ---------------------------------------- |
| `=`          | Equal                 | `age = 25`                               |
| `!=` or `<>` | Not equal             | `age != 25`                              |
| `>`          | Greater than          | `salary > 30000`                         |
| `<`          | Less than             | `age < 30`                               |
| `>=`         | Greater than or equal | `age >= 25`                              |
| `<=`         | Less than or equal    | `age <= 30`                              |
| AND          | Both conditions true  | `age > 20 AND salary > 30000`            |
| OR           | Either condition true | `department = 'IT' OR department = 'HR'` |
| NOT          | Negates a condition   | `NOT age > 25`                           |

### **More useful WHERE conditions**

**A. IN – Match multiple values**

```
SELECT *
FROM employees
WHERE department IN ('IT', 'HR');
```

Same idea as:

```
WHERE department = 'IT'
OR department = 'HR';
```

**B. BETWEEN – Find a range**

```
SELECT *
FROM employees
WHERE salary BETWEEN 25000 AND 45000;
```

Both endpoints are included.

**C. LIKE – Pattern matching**

```
SELECT *
FROM employees
WHERE name LIKE 'R%';
```

Finds names starting with R.

| Pattern  | Meaning               |
| -------- | --------------------- |
| `'R%'`   | Starts with R         |
| `'%a'`   | Ends with a           |
| `'%ha%'` | Contains ha           |
| `'_a%'`  | Second character is a |

**D. ILIKE – Case-insensitive pattern matching**

```
SELECT *
FROM employees
WHERE name ILIKE 'r%';
```

Matches both R and r.

**E. IS NULL**

```
SELECT *
FROM employees
WHERE department IS NULL;
```

Finds rows where department has no known value.

Remember:

```
WHERE department = NULL;
```

is incorrect. Use `IS NULL`.

### **Problems with WHERE and solutions**

| Problem                                | Solution                                     |
| -------------------------------------- | -------------------------------------------- |
| Using `= NULL`                         | Use `IS NULL`                                |
| Wrong AND / OR logic                   | Use parentheses                              |
| Pattern search is slow on large tables | Consider suitable indexes                    |
| Comparing incompatible data types      | Use appropriate data types or explicit casts |

Example of AND/OR confusion:

```
SELECT *
FROM employees
WHERE department = 'IT'
OR department = 'HR'
AND salary > 30000;
```

SQL evaluates AND before OR.

So it means:

```
WHERE department = 'IT'
OR (department = 'HR' AND salary > 30000);
```

If you want both departments to have salary above 30,000:

```
SELECT *
FROM employees
WHERE (department = 'IT' OR department = 'HR')
AND salary > 30000;
```

**Interview trick:** When mixing AND and OR, use parentheses to make your intention clear.

# **6. DISTINCT Clause**

**What?**

DISTINCT removes duplicate rows from the query result.

**Why?**

When you want unique values instead of repeated values.

**Syntax:**

```
SELECT DISTINCT column_name
FROM table_name;
```

Example:

```
SELECT DISTINCT department
FROM employees;
```

Output:

| department |
| ---------- |
| IT         |
| HR         |
| Finance    |

Even though IT and HR appear multiple times, they appear only once in the result.

### **DISTINCT on multiple columns**

```
SELECT DISTINCT department, age
FROM employees;
```

Important: It removes duplicate combinations of department and age, not duplicates in each column separately.

### **Problem with DISTINCT**

Sometimes beginners use DISTINCT to hide duplicate rows caused by incorrect JOIN conditions.

**Solution:** First check your JOIN logic. Use DISTINCT only when you actually need unique results.

**Interview question:** DISTINCT vs GROUP BY?

- DISTINCT removes duplicate result rows.
- GROUP BY groups rows, commonly to perform aggregate calculations.

# **7. GROUP BY Clause**

Very important for SQL interviews

**What?**

GROUP BY groups rows having the same values in specified columns.

**Why?**

To calculate information for each group.

For example:

- Total employees in each department.
- Average salary in each department.
- Maximum salary in each department.

**Syntax:**

```
SELECT column_name, AGGREGATE_FUNCTION()
FROM table_name
GROUP BY column_name;
```

### **Example 1: Count employees in each department**

```
SELECT department, COUNT(*)
FROM employees
GROUP BY department;
```

Output:

| department | count |
| ---------- | ----- |
| IT         | 2     |
| HR         | 2     |
| Finance    | 1     |

### **Example 2: Average salary by department**

```
SELECT department, AVG(salary)
FROM employees
GROUP BY department;
```

### **Important aggregate functions**

| Function | Purpose                       | Example       |
| -------- | ----------------------------- | ------------- |
| COUNT()  | Count rows or non-NULL values | `COUNT(*)`    |
| SUM()    | Total                         | `SUM(salary)` |
| AVG()    | Average                       | `AVG(salary)` |
| MAX()    | Highest value                 | `MAX(salary)` |
| MIN()    | Lowest value                  | `MIN(salary)` |

### **GROUP BY with multiple columns**

```
SELECT department, age, COUNT(*)
FROM employees
GROUP BY department, age;
```

Groups records by the combination of department and age.

### **Important GROUP BY rule**

If you select a normal column along with an aggregate function, that normal column generally needs to be included in GROUP BY (unless it is functionally dependent on the grouped columns).

Wrong

```
SELECT department, name, COUNT(*)
FROM employees
GROUP BY department;
```

Why? There can be multiple employee names in one department. SQL doesn't know which name to display.

Correct

```
SELECT department, COUNT(*)
FROM employees
GROUP BY department;
```

### **Problem with GROUP BY**

**Problem:** GROUP BY can return unexpected results when you group by too many columns.

**Solution:** Group only by the columns required for your calculation.

# **8. HAVING Clause**

**What?**

HAVING filters grouped results.

**Why?**

When you want to filter groups based on aggregate calculations.

**Syntax:**

```
SELECT column_name, AGGREGATE_FUNCTION()
FROM table_name
GROUP BY column_name
HAVING condition;
```

Example:

Find departments having more than one employee.

```
SELECT department, COUNT(*)
FROM employees
GROUP BY department
HAVING COUNT(*) > 1;
```

Output:

| department | count |
| ---------- | ----- |
| IT         | 2     |
| HR         | 2     |

### **WHERE vs HAVING**

Frequently asked interview question

| WHERE                                                    | HAVING                             |
| -------------------------------------------------------- | ---------------------------------- |
| Filters individual rows                                  | Filters groups                     |
| Used before GROUP BY logically                           | Used after GROUP BY logically      |
| Generally filters normal row values                      | Commonly filters aggregate results |
| Cannot directly use aggregate functions in its condition | Can use aggregate functions        |

### **Example using both**

Find departments whose average salary is above 30,000, considering only employees older than 24.

```
SELECT department, AVG(salary)
FROM employees
WHERE age > 24
GROUP BY department
HAVING AVG(salary) > 30000;
```

Understand the order:

1. WHERE filters employees older than 24.
2. GROUP BY groups the remaining employees by department.
3. AVG calculates average salary.
4. HAVING filters departments with average salary above 30,000.

### **Can we use HAVING without GROUP BY?**

Yes. It can filter the single implicit group formed by the query.

```
SELECT COUNT(*)
FROM employees
HAVING COUNT(*) > 3;
```

Returns the count if it is greater than 3; otherwise, no row.

### **Problem with HAVING**

Using HAVING when you only need to filter individual rows can be inefficient or unnecessarily complicated.

**Solution:** Use WHERE for row filtering and HAVING for group filtering.

# **9. ORDER BY Clause**

**What?**

ORDER BY sorts the query results.

**Why?**

To display data in ascending or descending order.

**Syntax:**

```
SELECT *
FROM table_name
ORDER BY column_name ASC;
```

### **ASC – Ascending**

```
SELECT *
FROM employees
ORDER BY salary ASC;
```

Lowest salary first.

### **DESC – Descending**

```
SELECT *
FROM employees
ORDER BY salary DESC;
```

Highest salary first.

### **Sort using multiple columns**

```
SELECT *
FROM employees
ORDER BY department ASC, salary DESC;
```

Meaning:

1. Sort departments alphabetically.
2. Within each department, show higher salaries first.

### **Sort using column position**

```
SELECT name, salary
FROM employees
ORDER BY 2 DESC;
```

`2` means the second selected column, which is salary.

This works, but using column names is generally easier to maintain.

### **NULLS FIRST and NULLS LAST**

PostgreSQL allows you to control where NULL values appear.

```
SELECT *
FROM employees
ORDER BY salary DESC NULLS LAST;
```

- NULLS FIRST = NULL values first.
- NULLS LAST = NULL values last.

### **Problem with ORDER BY**

**Problem:** Without ORDER BY, can we expect records in a fixed order?

No. SQL does not guarantee result order without ORDER BY.

**Solution:** Always use ORDER BY when the order matters.

# **10. LIMIT Clause**

**What?**

LIMIT restricts how many rows are returned.

**Why?**

Useful when you only need a few records.

**Syntax:**

```
SELECT *
FROM employees
LIMIT number;
```

Example:

```
SELECT *
FROM employees
LIMIT 3;
```

Returns at most 3 rows.

### **Find the highest-paid employee**

```
SELECT *
FROM employees
ORDER BY salary DESC
LIMIT 1;
```

This is a common interview question.

### **Find the second-highest salary**

One approach:

```
SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 1;
```

This returns the second-highest distinct salary.

### **Problem with LIMIT**

If you use LIMIT without ORDER BY, you cannot guarantee which records will be returned.

**Solution:**

```
SELECT *
FROM employees
ORDER BY salary DESC, id ASC
LIMIT 3;
```

The additional `id` sorting makes the ordering predictable when salaries are equal.

# **11. OFFSET Clause**

**What?**

OFFSET skips a specified number of rows before returning results.

**Why?**

Useful for pagination.

**Syntax:**

```
SELECT *
FROM employees
OFFSET number;
```

Example:

```
SELECT *
FROM employees
ORDER BY id
OFFSET 2;
```

Skips the first two rows and returns the remaining rows.

### **LIMIT + OFFSET**

Suppose you have 100 employees and want to display 10 employees per page.

| Page | LIMIT | OFFSET |
| ---- | ----- | ------ |
| 1    | 10    | 0      |
| 2    | 10    | 10     |
| 3    | 10    | 20     |
| 4    | 10    | 30     |

Formula:

\\[ OFFSET = (Page - 1) \times Limit \\]

Example: Page 3.

```
SELECT *
FROM employees
ORDER BY id
LIMIT 10 OFFSET 20;
```

### **Problem with OFFSET**

For large tables, high OFFSET values can become slow because PostgreSQL still has to find and skip earlier rows.

Also, when records are inserted or deleted between page requests, results can shift.

**Solution:** Use keyset pagination for large datasets.

Example:

```
SELECT *
FROM employees
WHERE id > 20
ORDER BY id
LIMIT 10;
```

This fetches the next 10 records after ID 20, assuming `id` is a unique, increasing key.

# **12. AS – Alias (Temporary Name)**

AS is used to give a temporary name to a column or table.

Strictly speaking, AS is a keyword, not a separate filtering or grouping clause.

### **Column alias**

```
SELECT
    name AS employee_name,
    salary AS monthly_salary
FROM employees;
```

### **Table alias**

```
SELECT e.name, e.salary
FROM employees AS e;
```

Why use aliases?

- Shorter queries.
- Better readability.
- Useful when joining multiple tables.

**Important:** A SELECT alias generally cannot be used in WHERE because WHERE is logically evaluated before SELECT.

Wrong:

```
SELECT salary * 12 AS annual_salary
FROM employees
WHERE annual_salary > 400000;
```

Correct:

```
SELECT salary * 12 AS annual_salary
FROM employees
WHERE salary * 12 > 400000;
```

You can generally use the SELECT alias in ORDER BY.

```
SELECT salary * 12 AS annual_salary
FROM employees
ORDER BY annual_salary DESC;
```

# **13. JOIN – Combining Multiple Tables**

JOIN is technically a FROM-clause construct, but it is one of the most important SQL topics.

Suppose you have two tables.

**employees**

| id | name  | department_id |
| -- | ----- | ------------- |
| 1  | Rahul | 101           |
| 2  | Priya | 102           |
| 3  | Amit  | 101           |

**departments**

| id  | department_name |
| --- | --------------- |
| 101 | IT              |
| 102 | HR              |
| 103 | Finance         |

### **INNER JOIN**

Returns only matching records.

```
SELECT e.name, d.department_name
FROM employees e
INNER JOIN departments d
ON e.department_id = d.id;
```

### **LEFT JOIN**

Returns all employees and matching department information. Unmatched departments appear as NULL.

```
SELECT e.name, d.department_name
FROM employees e
LEFT JOIN departments d
ON e.department_id = d.id;
```

### **RIGHT JOIN**

Returns all departments and matching employee information.

```
SELECT e.name, d.department_name
FROM employees e
RIGHT JOIN departments d
ON e.department_id = d.id;
```

### **FULL OUTER JOIN**

Returns all matching and non-matching rows from both tables.

```
SELECT e.name, d.department_name
FROM employees e
FULL OUTER JOIN departments d
ON e.department_id = d.id;
```

### **Common JOIN problem**

Suppose you want employees without a department.

Wrong approach:

```
SELECT *
FROM employees e
LEFT JOIN departments d
ON e.department_id = d.id
WHERE d.department_name = NULL;
```

Correct:

```
SELECT *
FROM employees e
LEFT JOIN departments d
ON e.department_id = d.id
WHERE d.id IS NULL;
```

Why? Use `IS NULL`, not `= NULL`.

# **14. UNION and UNION ALL**

These combine results from multiple SELECT queries.

### **UNION**

Combines results and removes duplicate rows.

```
SELECT name FROM employees
UNION
SELECT name FROM managers;
```

### **UNION ALL**

Combines results but keeps duplicates.

```
SELECT name FROM employees
UNION ALL
SELECT name FROM managers;
```

### **Difference**

| UNION                                         | UNION ALL              |
| --------------------------------------------- | ---------------------- |
| Removes duplicates                            | Keeps duplicates       |
| Usually requires extra duplicate-removal work | Usually faster         |
| Combines query results                        | Combines query results |

**Important rules:**

1. Both SELECT queries must return the same number of columns.
2. Corresponding columns must have compatible data types.
3. ORDER BY is applied to the combined result, not independently to each query.

Example:

```
SELECT name FROM employees
UNION ALL
SELECT name FROM managers
ORDER BY name;
```

**Common problem:** Using UNION when duplicates are meaningful.

**Solution:** Use UNION ALL when you want to preserve all records.

# **15. CASE – Conditional logic in SQL**

CASE is an expression, not a clause. It is commonly used inside SELECT, ORDER BY, and other expressions.

**Why?** To apply conditions and return different values.

Example:

```
SELECT
    name,
    salary,
    CASE
        WHEN salary >= 45000 THEN 'High'
        WHEN salary >= 30000 THEN 'Medium'
        ELSE 'Low'
    END AS salary_level
FROM employees;
```

Output:

| name  | salary | salary_level |
| ----- | ------ | ------------ |
| Rahul | 30000  | Medium       |
| Priya | 45000  | High         |
| Amit  | 25000  | Low          |
| Neha  | 50000  | High         |
| Sneha | 35000  | Medium       |

**Important:** CASE checks conditions from top to bottom and returns the first matching result.

# **16. WITH – CTE (Common Table Expression)**

CTE is used to create a temporary named result for a single SQL statement.

It makes complicated queries easier to read.

Example:

```
WITH high_salary AS (
    SELECT *
    FROM employees
    WHERE salary > 30000
)
SELECT *
FROM high_salary;
```

Meaning:

1. Create a temporary result named `high_salary`.
2. Store employees with salary above 30,000 in that result.
3. Read the result.

**Interview question: CTE vs Subquery?**

- Subquery: Query inside another query.
- CTE: Named query defined using WITH.
- CTE often makes complex queries easier to understand and reuse within one statement.

CTEs are not automatically faster than subqueries.

# **17. Window Functions – OVER and PARTITION BY**

These are advanced SQL concepts frequently asked in interviews.

Window functions perform calculations across related rows without combining them into one row per group.

Example:

```
SELECT
    name,
    department,
    salary,
    AVG(salary) OVER (
        PARTITION BY department
    ) AS department_avg
FROM employees;
```

What happens?

- PARTITION BY divides employees into departments.
- AVG calculates average salary for each department.
- Every employee row remains in the output.

### **Important window functions**

| Function     | Purpose                                |
| ------------ | -------------------------------------- |
| ROW_NUMBER() | Assigns unique sequential numbers      |
| RANK()       | Assigns ranks, leaving gaps after ties |
| DENSE_RANK() | Assigns ranks without gaps             |
| LAG()        | Gets a previous row's value            |
| LEAD()       | Gets a next row's value                |
| SUM() OVER   | Running or partitioned total           |
| AVG() OVER   | Average across a window                |

Example: Find the second-highest distinct salary.

```
SELECT *
FROM (
    SELECT
        name,
        salary,
        DENSE_RANK() OVER (
            ORDER BY salary DESC
        ) AS salary_rank
    FROM employees
) ranked
WHERE salary_rank = 2;
```

**Interview trick:** GROUP BY reduces rows into groups; window functions preserve individual rows.

# **18. SQL Query Execution Order**

Extremely important interview topic

This is one of the most common areas where beginners get confused.

We WRITE SQL in one order, but logically SQL processes the query in a different order.

### **Writing order**

```
SELECT
FROM
WHERE
GROUP BY
HAVING
ORDER BY
LIMIT
OFFSET;
```

### **Logical processing order**

1. **FROM / JOIN**

   Select source tables and combine rows.
2. **WHERE**

   Filter individual rows.
3. **GROUP BY**

   Group remaining rows.
4. **HAVING**

   Filter groups.
5. **SELECT**

   Calculate and choose output expressions.
6. **DISTINCT**

   Remove duplicate result rows.
7. **ORDER BY**

   Sort the result.
8. **LIMIT / OFFSET**

   Restrict and skip result rows.

This is the simplified logical processing order, not necessarily the physical execution plan chosen by PostgreSQL's query optimizer.

### **Complete example**

```
SELECT
    department,
    AVG(salary) AS avg_salary
FROM employees
WHERE age > 24
GROUP BY department
HAVING AVG(salary) > 30000
ORDER BY avg_salary DESC
LIMIT 2;
```

Understand each step:

1. FROM → Get employees.
2. WHERE → Keep employees older than 24.
3. GROUP BY → Group them by department.
4. HAVING → Keep departments with average salary above 30,000.
5. SELECT → Display department and average salary.
6. ORDER BY → Highest average salary first.
7. LIMIT → Return only two departments.

**Why is this important?**

Because it explains why:

- You cannot normally use SELECT aliases in WHERE.
- WHERE cannot directly use aggregate functions.
- HAVING can filter aggregate results.
- ORDER BY can generally use SELECT aliases.

# **19. Common SQL Problems and Their Solutions**

| Problem                          | Why it happens                    | Solution                                                                 |
| -------------------------------- | --------------------------------- | ------------------------------------------------------------------------ |
| Duplicate records                | Repeated data or incorrect JOIN   | Check JOIN conditions, use DISTINCT if needed                            |
| Wrong results with AND/OR        | Operator precedence               | Use parentheses                                                          |
| NULL comparison fails            | NULL represents unknown           | Use IS NULL / IS NOT NULL                                                |
| Aggregate in WHERE               | WHERE filters before grouping     | Use HAVING                                                               |
| Unexpected row order             | No guaranteed order               | Use ORDER BY                                                             |
| LIMIT returns unexpected records | No stable sorting                 | Use ORDER BY with unique tie-breaker                                     |
| Slow OFFSET                      | Many earlier rows need skipping   | Use keyset pagination                                                    |
| Slow WHERE query                 | Large scans or unsuitable indexes | Examine EXPLAIN ANALYZE and consider indexes                             |
| Slow SELECT \*                   | Fetching unnecessary columns      | Select required columns                                                  |
| Duplicate JOIN results           | One-to-many relationship          | Understand table relationships; aggregate or use EXISTS when appropriate |

## **20. Important PostgreSQL performance tips**

These are useful for real projects and experienced-level interviews.

**1. Use indexes for frequently searched columns.**

```
CREATE INDEX idx_employee_email
ON employees(email);
```

This can improve searches on email, depending on the query and data.

**2. Don't create indexes on every column.**

Why?

- Indexes consume storage.
- INSERT, UPDATE and DELETE may become slower because indexes must be maintained.

**3. Use EXPLAIN ANALYZE to understand query performance.**

```
EXPLAIN ANALYZE
SELECT *
FROM employees
WHERE salary > 30000;
```

It executes the query and displays its actual execution statistics.

**4. Use pagination for large result sets.**

```
SELECT *
FROM employees
ORDER BY id
LIMIT 20;
```

**5. Use appropriate data types and avoid unnecessary conversions.**

This helps correctness and can help PostgreSQL use indexes effectively.

# **21. Interview Questions – Important Differences**

These questions are frequently used to test your understanding.

| Question                     | Correct answer                             |
| ---------------------------- | ------------------------------------------ |
| WHERE vs HAVING?             | Rows vs groups                             |
| GROUP BY vs ORDER BY?        | Groups rows vs sorts rows                  |
| DISTINCT vs GROUP BY?        | Removes duplicates vs creates groups       |
| LIMIT vs OFFSET?             | Restricts rows vs skips rows               |
| UNION vs UNION ALL?          | Removes duplicates vs keeps duplicates     |
| INNER JOIN vs LEFT JOIN?     | Matching rows vs all left rows and matches |
| SELECT vs FROM?              | Selects output vs specifies data source    |
| CASE vs WHERE?               | Conditional expression vs row filtering    |
| CTE vs subquery?             | Named query vs nested query                |
| GROUP BY vs Window Function? | Collapses groups vs preserves rows         |

### **Some tricky interview questions**

**Q1. Can we use WHERE and HAVING together?**

Yes.

```
SELECT department, COUNT(*)
FROM employees
WHERE salary > 25000
GROUP BY department
HAVING COUNT(*) > 1;
```

**Q2. Can we use ORDER BY without GROUP BY?**

Yes.

```
SELECT *
FROM employees
ORDER BY salary DESC;
```

**Q3. Can we use GROUP BY without aggregate functions?**

Yes.

```
SELECT department
FROM employees
GROUP BY department;
```

This returns unique department groups. DISTINCT would usually be simpler here.

**Q4. Can we use multiple conditions in WHERE?**

Yes. Use AND, OR, NOT and parentheses.

**Q5. Which is executed first, WHERE or SELECT?**

Logically, WHERE comes before SELECT.

**Q6. Can we use aggregate functions in WHERE?**

Not directly. Use HAVING or a subquery.

**Q7. What happens if we don't use ORDER BY with LIMIT?**

You get some rows, but their order and selection are not guaranteed.

# **22. Practice Questions – Beginner to Advanced**

Use this table for practice:

```
CREATE TABLE employees (
    id INT PRIMARY KEY,
    name VARCHAR(50),
```

**My recommended learning order:**

1. First master SELECT, WHERE, AND, OR, IN, BETWEEN, LIKE.
2. Then GROUP BY, aggregate functions and HAVING.
3. Then ORDER BY, LIMIT and OFFSET.
4. Then JOINS and subqueries.
5. Finally CTEs, window functions and query optimization.

One important thing: Don't just memorize clause definitions. Practise writing queries and predicting their output. That is how you become confident in SQL interviews and real backend development.
