Yes! In SQL interviews, they commonly give you **two or three table structures, CREATE TABLE queries, or a real-world scenario** and ask you to identify the relationship.

Sometimes they don't directly ask "What is the relationship?" They ask you to design the tables or write a JOIN query.

Let's understand the practical interview procedure.

# **1. How interview questions are asked**

There are 4 common formats.

**Type 1: Given two tables**

```
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT REFERENCES customers(customer_id)
);
```

Question: Identify the relationship.

Your thinking:

1. Find the PK → `customers.customer_id`
2. Find the FK → `orders.customer_id`
3. FK is in orders table.
4. FK is not UNIQUE, so multiple orders can belong to one customer.

Answer: One-to-Many

One customer → Many orders.

**Type 2: Given a real-world scenario**

Question: A student can enroll in multiple courses. A course can have multiple students. Design the relationship.

Your thinking:

1. Identify entities → Students and Courses.
2. Check both sides → Both can have multiple records.
3. Relationship → Many-to-Many.
4. Create junction table → Enrollments.
5. Add both FKs.

```
CREATE TABLE enrollments (
    student_id INT REFERENCES students(student_id),
    course_id INT REFERENCES courses(course_id),
    PRIMARY KEY (student_id, course_id)
);
```

**Type 3: Given three tables**

```
CREATE TABLE employees (
    emp_id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE projects (
    project_id INT PRIMARY KEY,
    project_name VARCHAR(50)
);

CREATE TABLE employee_projects (
    emp_id INT REFERENCES employees(emp_id),
    project_id INT REFERENCES projects(project_id),
    PRIMARY KEY (emp_id, project_id)
);
```

Question: Identify the relationship.

Answer:

- Employees → Employee_Projects = 1:N
- Projects → Employee_Projects = 1:N
- Employees ↔ Projects = M:N

**Type 4: Asked to create a relationship**

Question: One person can have only one passport. Design tables.

```
CREATE TABLE persons (
    person_id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE passports (
    passport_id INT PRIMARY KEY,
    person_id INT UNIQUE REFERENCES persons(person_id)
);
```

Answer: One-to-One (at most one passport per person).

# **2. Practical procedure to solve any relationship question**

Follow these 5 steps in interviews.

1. **Identify entities**

   Example: Students, Courses, Teachers, Orders.
2. **Identify primary keys**

   Which column uniquely identifies each record?
3. **Identify foreign keys**

   Which column connects one table to another?
4. **Check cardinality**

   Ask: Can one record connect to multiple records on each side?
5. **Choose relationship**

   1:1, 1:N, M:N, or self-referencing.

# **4. Important interview tricks**

| Question clue                            | Think about                             |
| ---------------------------------------- | --------------------------------------- |
| One customer, many orders                | 1:N                                     |
| One student, many courses and vice versa | M:N                                     |
| One person, one passport                 | 1:1                                     |
| Employee has manager                     | Self-referencing                        |
| Two FKs in third table                   | Usually M:N                             |
| FK + UNIQUE                              | At most 1:1                             |
| FK without UNIQUE                        | Usually N:1 from FK table's perspective |

**Important:** Don't identify relationships only by table names. Read the business requirement and constraints. A foreign key without UNIQUE allows multiple child rows, but business rules may impose additional restrictions.

## **5. How to answer confidently in an interview**

Use this answer format:

"I identified the primary key and foreign key. The foreign key is in the orders table and is not unique, so multiple orders can reference one customer. Therefore, the relationship is One-to-Many."

This shows the interviewer your reasoning, not just your final answer.

**Next step:** Practice designing relationships from real-world scenarios, then write `CREATE TABLE` and `JOIN` queries. That's how you'll become comfortable with practical SQL interview questions.

`CONSTRAINT fk_product` means **giving a name to a constraint**.

Let's understand your code:

```
CONSTRAINT fk_product
    FOREIGN KEY (product_id)
    REFERENCES products(product_id)
    ON DELETE CASCADE
```

| Part                              | Meaning                                                      |
| --------------------------------- | ------------------------------------------------------------ |
| `CONSTRAINT`                      | Defines a named constraint                                   |
| `fk_product`                      | Name given to the constraint                                 |
| `FOREIGN KEY (product_id)`        | Makes product_id a foreign key                               |
| `REFERENCES products(product_id)` | Connects to product_id in products table                     |
| `ON DELETE CASCADE`               | If a product is deleted, its related orders are also deleted |

### **Why write&#x20;**`fk_product`**?**

So you can easily identify, manage or delete that constraint later.

Example:

```
ALTER TABLE orders
DROP CONSTRAINT fk_product;
```

This removes the foreign key constraint, not the column.

### **Can we write without CONSTRAINT name?**

Yes!

```
FOREIGN KEY (product_id)
REFERENCES products(product_id)
ON DELETE CASCADE
```

PostgreSQL automatically generates a constraint name.

### **Interview trick**

Common naming conventions:

| Constraint  | Naming example |
| ----------- | -------------- |
| Foreign Key | `fk_product`   |
| Primary Key | `pk_orders`    |
| Unique      | `uq_email`     |
| Check       | `chk_quantity` |

**Remember:** `fk_product` is just a custom name. It is not a SQL keyword or special function. You can choose another meaningful name, such as `fk_orders_product`.
