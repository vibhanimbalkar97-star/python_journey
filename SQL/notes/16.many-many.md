# **Many-to-Many (M:N) Relationship in SQL – Beginner to Advanced**

## **1. What is a Many-to-Many relationship?**

A **Many-to-Many relationship** means:

- One record in Table A can be related to multiple records in Table B.
- One record in Table B can also be related to multiple records in Table A.

**Example: Students and Courses**

- One student can enroll in many courses.
- One course can have many students.

## **2. Why do we need a junction table?**

We cannot properly represent a many-to-many relationship using just one foreign key in either table.

We use a third table called:

- Junction table
- Bridge table
- Linking table
- Associative table

All these terms mean essentially the same thing.

Example:

**Students**

| student_id (PK) | name  |
| --------------- | ----- |
| 1               | Rahul |
| 2               | Priya |

**Courses**

| course_id (PK) | course_name |
| -------------- | ----------- |
| 101            | Python      |
| 102            | SQL         |
| 103            | React       |

**Enrollments (Junction Table)**

| student_id (FK) | course_id (FK) |
| --------------- | -------------- |
| 1               | 101            |
| 1               | 102            |
| 2               | 101            |
| 2               | 103            |

Notice:

- Rahul → Python, SQL
- Priya → Python, React
- Python → Rahul, Priya

That's many-to-many!

## **3. How to create tables in PostgreSQL?**

**Step 1: Create Students**

```
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name VARCHAR(50)
);
```

**Step 2: Create Courses**

```
CREATE TABLE courses (
    course_id INT PRIMARY KEY,
    course_name VARCHAR(50)
);
```

**Step 3: Create Junction Table**

```
CREATE TABLE enrollments (
    student_id INT,
    course_id INT,

    PRIMARY KEY (student_id, course_id),

    FOREIGN KEY (student_id)
    REFERENCES students(student_id),

    FOREIGN KEY (course_id)
    REFERENCES courses(course_id)
);
```

### **Understand these terms**

| Term                  | Meaning                                  |
| --------------------- | ---------------------------------------- |
| PK                    | Primary Key – uniquely identifies a row  |
| FK                    | Foreign Key – connects to another table  |
| Junction table        | Connects two tables                      |
| Composite PK          | Primary key made from multiple columns   |
| Referential integrity | Ensures FK references a valid parent row |

## **4. Why use a composite primary key?**

```
PRIMARY KEY (student_id, course_id)
```

It means the combination must be unique.

Example:

| student_id | course_id | Allowed?                   |
| ---------- | --------- | -------------------------- |
| 1          | 101       | Yes                        |
| 1          | 102       | Yes                        |
| 2          | 101       | Yes                        |
| 1          | 101       | No – duplicate combination |

**Interview trick:** A student can enroll in multiple courses, but the same student-course pair cannot be inserted twice.

If you need to track enrollment by semester, you could use:

```
PRIMARY KEY (student_id, course_id, semester)
```

Now the same student can enroll in the same course in different semesters.

## **5. How to insert data?**

```
INSERT INTO students VALUES
(1, 'Rahul'),
(2, 'Priya');

INSERT INTO courses VALUES
(101, 'Python'),
(102, 'SQL');

INSERT INTO enrollments VALUES
(1, 101),
(1, 102),
(2, 101);
```

**Important:** Insert parent records first, then junction-table records. Otherwise, the foreign key may fail.

## **6. How to fetch Many-to-Many data using JOIN?**

This is very important for interviews.

**Question: Get all students with their courses.**

```
SELECT
    s.name,
    c.course_name
FROM students s
JOIN enrollments e
    ON s.student_id = e.student_id
JOIN courses c
    ON e.course_id = c.course_id;
```

Result:

| name  | course_name |
| ----- | ----------- |
| Rahul | Python      |
| Rahul | SQL         |
| Priya | Python      |

**Understand the JOIN flow:**

**Students**

student_id

**Enrollments (Junction Table)**

course_id

**Courses**

**Trick:** For M:N JOIN, remember:

`Table A → Junction Table → Table B`

You usually need two JOIN conditions.

## **7. How to find students who enrolled in Python?**

```
SELECT s.name
FROM students s
JOIN enrollments e
    ON s.student_id = e.student_id
JOIN courses c
    ON e.course_id = c.course_id
WHERE c.course_name = 'Python';
```

## **8. How to count courses per student?**

```
SELECT
    s.name,
    COUNT(e.course_id) AS total_courses
FROM students s
LEFT JOIN enrollments e
    ON s.student_id = e.student_id
GROUP BY s.student_id, s.name;
```

Why `LEFT JOIN`?

To include students who have not enrolled in any course.

Why `COUNT(e.course_id)` instead of `COUNT(*)`?

Because `COUNT(*)` counts the unmatched student row too, while `COUNT(e.course_id)` ignores NULL.

## **9. Advanced concepts for interviews**

**A. Can a junction table have extra columns?**

Yes! It can store information about the relationship itself.

Example:

```
CREATE TABLE enrollments (
    student_id INT REFERENCES students(student_id),
    course_id INT REFERENCES courses(course_id),
    enrolled_at DATE DEFAULT CURRENT_DATE,
    status VARCHAR(20) DEFAULT 'active',

    PRIMARY KEY (student_id, course_id)
);
```

Here, `enrolled_at` and `status` describe the enrollment relationship.

**B. Composite PK vs Surrogate PK**

| Composite PK                       | Surrogate PK                          |
| ---------------------------------- | ------------------------------------- |
| Uses both FK columns               | Uses separate ID                      |
| `(student_id, course_id)`          | `enrollment_id`                       |
| Naturally prevents duplicate pairs | Needs `UNIQUE(student_id, course_id)` |

Surrogate-key example:

```
CREATE TABLE enrollments (
    enrollment_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    student_id INT REFERENCES students(student_id),
    course_id INT REFERENCES courses(course_id),

    UNIQUE (student_id, course_id)
);
```

**C. ON DELETE CASCADE**

What happens when a student is deleted?

```
FOREIGN KEY (student_id)
REFERENCES students(student_id)
ON DELETE CASCADE
```

It automatically deletes that student's enrollment rows.

It does not delete the course records.

**D. Indexing**

PostgreSQL automatically creates indexes for primary keys and unique constraints, but not for foreign-key columns.

For queries that frequently search courses by ID in enrollments:

```
CREATE INDEX idx_enrollments_course
ON enrollments(course_id);
```

The composite PK `(student_id, course_id)` already creates an index starting with `student_id`, but it may not efficiently support searches by `course_id` alone.

## **10. Common interview mistakes**

| Mistake                                         | Correct approach                    |
| ----------------------------------------------- | ----------------------------------- |
| Storing multiple course IDs in one column       | Use junction table                  |
| Keeping only one FK in students                 | Use two FKs in junction table       |
| Forgetting duplicate prevention                 | Composite PK or UNIQUE              |
| Joining only two tables                         | Join all three tables               |
| Inserting junction rows before parents          | Insert parents first                |
| Assuming FK automatically creates an index      | Create indexes when needed          |
| Deleting a parent without checking dependencies | Choose ON DELETE behavior carefully |

## **11. Interview: Steps to identify Many-to-Many**

Remember these 5 steps:

1. Identify two entities: Students and Courses.
2. Ask: Can one student have many courses? Yes.
3. Ask: Can one course have many students? Yes.
4. Create a third table: Enrollments.
5. Add both foreign keys and a composite PK or UNIQUE constraint.

**Golden trick:** If both sides can have multiple records, think M:N → Junction Table.
