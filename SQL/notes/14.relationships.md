# **SQL Relationships — Beginner to Pro (PostgreSQL)**

Relationships in SQL describe **how two or more tables are connected using common columns**.

Instead of storing all information in one huge table, we divide data into separate tables and connect them using **Primary Keys (PK) and Foreign Keys (FK)**.

Hindi: Relationships ka matlab hai do ya zyada tables ko aapas mein connect karna.

## **1. Why do we need relationships?**

Imagine a student management system.

Without relationships, you might store everything in one table:

| student_id | student_name | course_name | teacher_name |
| ---------- | ------------ | ----------- | ------------ |
| 1          | Amit         | Python      | Rahul        |
| 2          | Priya        | Python      | Rahul        |
| 3          | Neha         | React       | Sneha        |

Problems:

- Teacher names are repeated.
- Course information is repeated.
- Updating teacher details requires multiple changes.
- Data duplication can cause inconsistency.

**Better approach:** Create separate tables and connect them.

**students**

| student_id (PK) | student_name |
| --------------- | ------------ |
| 1               | Amit         |
| 2               | Priya        |
| 3               | Neha         |

**courses**

| course_id (PK) | course_name |
| -------------- | ----------- |
| 101            | Python      |
| 102            | React       |

**teachers**

| teacher_id (PK) | teacher_name |
| --------------- | ------------ |
| 1               | Rahul        |
| 2               | Sneha        |

Now we connect the tables using IDs.

## **2. First understand Primary Key and Foreign Key**

These two concepts are the foundation of SQL relationships.

### **Primary Key (PK)**

A column that uniquely identifies each row in a table.

```
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(50)
);
```

Rules:

- Must be unique.
- Cannot be NULL.
- A table has only one primary key constraint (it can contain multiple columns).

### **Foreign Key (FK)**

A column that refers to a primary key or unique key in another table.

```
CREATE TABLE courses (
    course_id INT PRIMARY KEY,
    course_name VARCHAR(50)
);

CREATE TABLE students (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(50),
    course_id INT REFERENCES courses(course_id)
);
```

Here:

- `courses.course_id` = Primary Key.
- `students.course_id` = Foreign Key.

The foreign key ensures that a student cannot reference a course ID that does not exist.

**Important:** A foreign key can contain NULL unless you also specify `NOT NULL`.

### **PK vs FK**

| Primary Key                 | Foreign Key                      |
| --------------------------- | -------------------------------- |
| Identifies a row            | Connects tables                  |
| Unique                      | Can have duplicates              |
| Cannot be NULL              | Can be NULL unless NOT NULL      |
| One PK constraint per table | Multiple FK constraints possible |
| Parent/referenced key       | Child/referencing key            |

## **4. One-to-One relationship (1:1)**

**Real-world example:** Person and Passport.

One person has one passport, and one passport belongs to one person.

### **How to create it**

```
CREATE TABLE persons (
    person_id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE passports (
    passport_id INT PRIMARY KEY,
    passport_number VARCHAR(30) UNIQUE,
    person_id INT UNIQUE REFERENCES persons(person_id)
);
```

Why `UNIQUE` on `person_id`?

Because without UNIQUE, multiple passports could reference the same person. Adding UNIQUE ensures each person can be referenced by at most one passport.

**Where to use:**

- Person and passport
- User and user profile (when separate)
- Employee and employee details

**Interview trick:** A foreign key alone does not create a one-to-one relationship. Add `UNIQUE` to the foreign key.

## **5. One-to-Many relationship (1:N)**

**Real-world example:** Department and Employees.

- One department has many employees.
- One employee belongs to one department.

### **How to create it**

```
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(50)
);

CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(50),
    department_id INT REFERENCES departments(department_id)
);
```

Sample data:

**departments**

| department_id | department_name |
| ------------- | --------------- |
| 1             | IT              |
| 2             | HR              |

**employees**

| employee_id | employee_name | department_id |
| ----------- | ------------- | ------------- |
| 101         | Amit          | 1             |
| 102         | Priya         | 1             |
| 103         | Rahul         | 2             |

Here, IT has two employees. Both employees refer to department ID 1.

Important interview rule

In a one-to-many relationship, put the foreign key on the **many side (child table)**.

Example: `employees.department_id` references `departments.department_id`.

**Where to use:**

- Department → Employees
- Customer → Orders
- Category → Products
- Author → Books (if each book has one author)

## **6. Many-to-Many relationship (M:N)**

**Real-world example:** Students and Courses.

- One student can join multiple courses.
- One course can have multiple students.

Can we directly put one foreign key in students or courses?

No. One foreign key alone cannot represent all these connections cleanly.

We use a **junction table** (also called bridge or mapping table).

### **Step 1: Create students**

```
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    student_name VARCHAR(50)
);
```

### **Step 2: Create courses**

```
CREATE TABLE courses (
    course_id INT PRIMARY KEY,
    course_name VARCHAR(50)
);
```

### **Step 3: Create junction table**

```
CREATE TABLE student_courses (
    student_id INT REFERENCES students(student_id),
    course_id INT REFERENCES courses(course_id),
    enrolled_on DATE DEFAULT CURRENT_DATE,

    PRIMARY KEY (student_id, course_id)
);
```

Why two foreign keys?

- `student_id` connects to students.
- `course_id` connects to courses.

Why composite primary key?

`PRIMARY KEY (student_id, course_id)` prevents the same student from enrolling in the same course twice.

Example:

**student_courses**

| student_id | course_id |
| ---------- | --------- |
| 1          | 101       |
| 1          | 102       |
| 2          | 101       |
| 3          | 102       |

This means:

- Student 1 joined courses 101 and 102.
- Students 1 and 2 joined course 101.
- Students 1 and 3 joined course 102.

**Where to use:**

- Students ↔ Courses
- Users ↔ Roles
- Products ↔ Orders (when an order contains many products and a product can appear in many orders)
- Doctors ↔ Patients

## **7. Self-referencing relationship**

A table refers to itself through a foreign key.

Example: Employees and their managers.

```
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(50),
    manager_id INT REFERENCES employees(employee_id)
);
```

Example data:

| employee_id | employee_name | manager_id |
| ----------- | ------------- | ---------- |
| 1           | Rahul         | NULL       |
| 2           | Amit          | 1          |
| 3           | Priya         | 1          |
| 4           | Neha          | 2          |

Here:

- Rahul has no manager.
- Amit's manager is Rahul.
- Priya's manager is Rahul.
- Neha's manager is Amit.

**Where to use:**

- Employee-manager hierarchy
- Category and subcategory
- Organization hierarchy
- Comments and replies

## **8. Difference between all relationships**

| Relationship     | Meaning                  | Where FK goes                     |
| ---------------- | ------------------------ | --------------------------------- |
| One-to-One       | One A ↔ One B            | Usually either table, with UNIQUE |
| One-to-Many      | One A → Many B           | Many/child table                  |
| Many-to-Many     | Many A ↔ Many B          | Junction table                    |
| Self-referencing | Table connects to itself | Same table                        |

**Easy trick to remember:**

- 1:1 → FK + UNIQUE
- 1:N → FK on many side
- M:N → Two FKs in junction table
- Self → FK references same table

## **9. Relationships vs JOIN — Important difference**

These are related but not the same.

**Relationship:** Defines how tables are connected in the database using keys.

**JOIN:** A SQL query operation that retrieves related data from multiple tables.

Example: We have `employees.department_id` connected to `departments.department_id`.

To retrieve employee names with department names:

```
SELECT
    e.employee_name,
    d.department_name
FROM employees e
INNER JOIN departments d
ON e.department_id = d.department_id;
```

Result:

| employee_name | department_name |
| ------------- | --------------- |
| Amit          | IT              |
| Priya         | IT              |
| Rahul         | HR              |

Remember: A foreign key creates a database relationship. JOIN uses a matching condition to combine rows. You can also JOIN tables without declared foreign keys.

## **10. Referential integrity — What happens when parent data is deleted?**

Suppose an employee refers to department ID 1.

What happens if someone deletes department ID 1?

PostgreSQL provides foreign key actions.

```
FOREIGN KEY (department_id)
REFERENCES departments(department_id)
ON DELETE CASCADE
```

### **Important ON DELETE options**

| Action        | Meaning                                                              |
| ------------- | -------------------------------------------------------------------- |
| `CASCADE`     | Delete related child rows                                            |
| `SET NULL`    | Set child FK to NULL                                                 |
| `SET DEFAULT` | Set child FK to its default                                          |
| `RESTRICT`    | Prevent deletion while child rows exist                              |
| `NO ACTION`   | Check the constraint; usually behaves like RESTRICT at statement end |

Example:

```
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(50),
    department_id INT,
    FOREIGN KEY (department_id)
        REFERENCES departments(department_id)
        ON DELETE SET NULL
);
```

If a department is deleted, employees belonging to it remain, but their `department_id` becomes NULL.

**Important:** `SET NULL` requires the foreign key column to allow NULL. `SET DEFAULT` requires a valid default value that satisfies the foreign key.

### **ON UPDATE**

You can also specify what happens when the referenced key changes.

```
FOREIGN KEY (department_id)
REFERENCES departments(department_id)
ON UPDATE CASCADE
```

If the department ID changes, matching employee foreign keys are updated too.

**Interview tip:** `ON DELETE CASCADE` deletes child records automatically. Use it only when that deletion is actually desired.

## **11. Optional vs Mandatory relationships**

This is another important interview concept.

A relationship can be mandatory or optional.

Example: An employee may or may not belong to a department.

```
department_id INT REFERENCES departments(department_id)
```

Here, `department_id` can be NULL, so department assignment is optional.

```
department_id INT NOT NULL REFERENCES departments(department_id)
```

Here, every employee must have a department.

| Rule              | Meaning                                            |
| ----------------- | -------------------------------------------------- |
| Nullable FK       | Relationship is optional for the child             |
| NOT NULL FK       | Relationship is mandatory for the child            |
| UNIQUE FK         | Each parent can be referenced by at most one child |
| FK without UNIQUE | Parent can be referenced by multiple children      |

Important: A foreign key does not force every parent to have a child. For example, a department can exist with zero employees.

## **12. Composite foreign key — Advanced**

A composite key uses multiple columns together to identify a record.

Example: A student can enroll in a particular course only once per semester.

```
CREATE TABLE student_courses (
    student_id INT,
    course_id INT,
    semester VARCHAR(20),

    PRIMARY KEY (student_id, course_id, semester)
);
```

Here, all three columns together identify a unique enrollment.

A composite foreign key can also reference a composite primary key:

```
CREATE TABLE course_details (
    course_id INT,
    semester VARCHAR(20),
    course_name VARCHAR(50),

    PRIMARY KEY (course_id, semester)
);

CREATE TABLE enrollments (
    enrollment_id INT PRIMARY KEY,
    course_id INT,
    semester VARCHAR(20),

    FOREIGN KEY (course_id, semester)
    REFERENCES course_details(course_id, semester)
);
```

**Remember:** The number and order of columns in the foreign key must match the referenced key.

## **13. Add relationships to existing tables using ALTER**

You don't always need to create relationships when creating tables. You can add them later.

Example:

```
ALTER TABLE employees
ADD CONSTRAINT fk_department
FOREIGN KEY (department_id)
REFERENCES departments(department_id);
```

Add UNIQUE for one-to-one:

```
ALTER TABLE passports
ADD CONSTRAINT unique_person
UNIQUE(person_id);
```

Remove a foreign key:

```
ALTER TABLE employees
DROP CONSTRAINT fk_department;
```

**Important:** Before adding a foreign key, check that existing values have matching parent IDs. Otherwise, PostgreSQL will reject the constraint.

Find invalid department IDs:

```
SELECT e.*
FROM employees e
LEFT JOIN departments d
ON e.department_id = d.department_id
WHERE e.department_id IS NOT NULL
AND d.department_id IS NULL;
```

## **14. Relationships and normalization**

Normalization means organizing data to reduce duplication and avoid data inconsistencies.

| Normal form | Simple meaning                                                   |
| ----------- | ---------------------------------------------------------------- |
| 1NF         | Store atomic values; avoid repeating groups                      |
| 2NF         | No partial dependency on part of a composite candidate key       |
| 3NF         | No transitive dependency of non-key attributes on candidate keys |

Example:

Instead of storing department name repeatedly in every employee record, store it once in `departments` and reference it using `department_id`.

Benefits:

- Less duplicate data.
- Easier updates.
- Better consistency.
- Easier maintenance.

**Interview tip:** Relationships help implement normalized database designs, but normalization and relationships are not exactly the same thing.

## **15. Real-world database design example**

Imagine you are building an e-commerce application.

**Database relationship design**

**CUSTOMERS**

`customer_id (PK)`

`name`

One customer → many orders

**ORDERS**

`order_id (PK)`

`customer_id (FK)`

One order → many order items

**ORDER_ITEMS**

`order_id (FK)`

`product_id (FK)`

`quantity`

Each item refers to a product

**PRODUCTS**

`product_id (PK)`

`product_name`

`price`

Here:

- Customers → Orders = One-to-Many.
- Orders → Products = Many-to-Many through `order_items`.
- Products → Order Items = One-to-Many.

This is a common real-world database structure.

## **16. Steps to solve any relationship question in an interview**

When an interviewer gives you a real-world scenario, follow these steps.

1. **Identify the entities**

   Ask: What are the main things?

   Example: Students and Courses.
2. **Identify the relationship**

   Ask: Can one student have many courses? Can one course have many students?

   If both are yes → Many-to-Many.
3. **Identify the primary keys**

   Every table needs a way to uniquely identify its records.
4. **Place foreign keys correctly**
   - 1:1 → FK with UNIQUE.
   - 1:N → FK on the many side.
   - M:N → Junction table.
5. **Decide optional or mandatory**

   Can the FK be NULL? Should it be NOT NULL?
6. **Choose delete/update behavior**

   Decide whether to use CASCADE, SET NULL, RESTRICT, etc.
7. **Write CREATE TABLE queries and test**

   Insert sample records and check whether invalid relationships are rejected.

### **Example interview scenario**

Question: A customer can place multiple orders. Every order belongs to one customer. What relationship is this?

Think:

1. One customer → many orders.
2. One order → one customer.
3. Therefore, One-to-Many.
4. FK belongs in the `orders` table.

```
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    customer_name VARCHAR(50)
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    order_date DATE,
    customer_id INT NOT NULL,
    FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
);
```

That's the complete reasoning expected in an interview.

## **17. Common interview differences**

| Question                      | Answer                                                         |
| ----------------------------- | -------------------------------------------------------------- |
| Relationship vs JOIN          | Relationship defines a connection; JOIN retrieves related rows |
| PK vs FK                      | PK identifies a record; FK references another key              |
| UNIQUE vs PK                  | UNIQUE allows NULL by default; PK does not                     |
| 1:1 vs 1:N                    | 1:1 has at most one matching child; 1:N allows many            |
| 1:N vs M:N                    | M:N needs a junction table                                     |
| CASCADE vs SET NULL           | CASCADE deletes children; SET NULL keeps children              |
| Composite PK vs single PK     | Composite uses multiple columns; single uses one               |
| Normalization vs relationship | Normalization organizes data; relationships connect tables     |

## **18. Common mistakes to avoid**

1. **Putting FK on the wrong side:** For 1:N, put it on the many side.
2. **Forgetting UNIQUE in 1:1:** A normal FK permits duplicate references.
3. **Directly connecting M:N:** Use a junction table.
4. **Forgetting FK data validation:** Existing child IDs must match parent IDs.
5. **Using CASCADE everywhere:** It may delete important data.
6. **Confusing JOIN with relationship:** A JOIN does not automatically create a foreign key.
7. **Forgetting indexes:** PostgreSQL automatically indexes primary and unique keys, but it does not automatically create an index on the referencing FK column. Add one when query patterns benefit from it.
