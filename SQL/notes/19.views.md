# **SQL Views – Complete Guide (Beginner to Advanced)**

## **1. What is a View?**

A **View is a virtual table created using a SQL query.**

It does not normally store the actual result data. It stores the SQL query, and when you access the view, PostgreSQL executes that query against the underlying tables.

Simple example:

Suppose you have an `employees` table with 10 columns, but you frequently need only employee names and salaries.

Instead of writing the same SELECT query again and again, create a View.

```
CREATE VIEW employee_details AS
SELECT name, salary
FROM employees;
```

Now you can use:

```
SELECT * FROM employee_details;
```

It's like creating a reusable SELECT query.

## **2. Why use Views?**

| Reason           | Explanation                               |
| ---------------- | ----------------------------------------- |
| Reusability      | Avoid writing the same query repeatedly   |
| Simplicity       | Hide complicated JOIN queries             |
| Security         | Show only selected columns or rows        |
| Readability      | Make complex queries easier to understand |
| Data abstraction | Users work with a simpler virtual table   |
| Maintainability  | Reuse a common query in multiple places   |

**Real-world examples:**

- Banking: Show account balance without exposing sensitive details.
- E-commerce: Show product names and prices.
- HR: Show employee names and departments without exposing salaries.
- Reporting: Combine sales, customers and products into one view.

## **3. How to create a View?**

Syntax:

```
CREATE VIEW view_name AS
SELECT column1, column2
FROM table_name
WHERE condition;
```

Example:

```
CREATE VIEW active_employees AS
SELECT emp_id, name, department
FROM employees
WHERE status = 'active';
```

Use the view:

```
SELECT * FROM active_employees;
```

Filter the view:

```
SELECT *
FROM active_employees
WHERE department = 'IT';
```

Sort the view:

```
SELECT *
FROM active_employees
ORDER BY name;
```

**Important:** You can use a View like a table in SELECT queries.

## **4. View with WHERE, JOIN, GROUP BY and functions**

A View can contain almost any SELECT query.

**A. View with WHERE**

```
CREATE VIEW high_salary_employees AS
SELECT name, salary
FROM employees
WHERE salary > 50000;
```

**B. View with JOIN**

```
CREATE VIEW employee_department AS
SELECT
    e.emp_id,
    e.name,
    d.dept_name
FROM employees e
JOIN departments d
    ON e.dept_id = d.dept_id;
```

Now:

```
SELECT * FROM employee_department;
```

No need to write JOIN again!

**C. View with GROUP BY and aggregate functions**

```
CREATE VIEW department_salary AS
SELECT
    dept_id,
    COUNT(*) AS total_employees,
    AVG(salary) AS average_salary
FROM employees
GROUP BY dept_id;
```

**D. View with HAVING**

```
CREATE VIEW large_departments AS
SELECT dept_id, COUNT(*) AS total
FROM employees
GROUP BY dept_id
HAVING COUNT(*) > 5;
```

**E. View with CASE**

```
CREATE VIEW employee_categories AS
SELECT
    name,
    salary,
    CASE
        WHEN salary >= 50000 THEN 'High'
        ELSE 'Low'
    END AS salary_category
FROM employees;
```

## **5. How to modify a View?**

### **CREATE OR REPLACE VIEW**

Use this when you want to change an existing View's query.

```
CREATE OR REPLACE VIEW active_employees AS
SELECT emp_id, name, salary
FROM employees
WHERE status = 'active';
```

It replaces the existing view definition.

**Important rules:**

- Existing columns must remain in the same order with compatible names and data types.
- You can add new columns at the end.
- You cannot use it to freely rename or remove existing output columns.

### **ALTER VIEW**

Use it to change View properties or rename it.

Rename:

```
ALTER VIEW active_employees
RENAME TO current_employees;
```

Change owner:

```
ALTER VIEW current_employees
OWNER TO admin_user;
```

Change schema:

```
ALTER VIEW current_employees
SET SCHEMA reporting;
```

### **DROP VIEW**

Delete a View:

```
DROP VIEW current_employees;
```

Safer version:

```
DROP VIEW IF EXISTS current_employees;
```

Multiple views:

```
DROP VIEW view1, view2;
```

`CASCADE`:

```
DROP VIEW view1 CASCADE;
```

Deletes dependent objects too. Use carefully.

`RESTRICT`:

```
DROP VIEW view1 RESTRICT;
```

Prevents dropping the view if dependent objects exist. This is the default behavior.

## **6. Can we INSERT, UPDATE and DELETE using a View?**

Yes, but only certain views are automatically updatable in PostgreSQL.

A simple view based on one table is generally updatable.

Example:

```
CREATE VIEW employee_view AS
SELECT emp_id, name, salary
FROM employees;
```

**INSERT through View**

```
INSERT INTO employee_view
VALUES (10, 'Rahul', 60000);
```

This inserts into the underlying `employees` table.

**UPDATE through View**

```
UPDATE employee_view
SET salary = 70000
WHERE emp_id = 10;
```

**DELETE through View**

```
DELETE FROM employee_view
WHERE emp_id = 10;
```

These operations affect the original table, not a separate copy.

### **When is a View NOT automatically updatable?**

Usually, a View containing these features is not automatically updatable:

- GROUP BY
- HAVING
- DISTINCT
- Aggregate functions like SUM, AVG, COUNT
- UNION
- Window functions
- Certain JOINs and computed expressions

For example:

```
CREATE VIEW department_count AS
SELECT dept_id, COUNT(*)
FROM employees
GROUP BY dept_id;
```

You cannot directly update the aggregate result like a normal table.

**Advanced:** PostgreSQL supports INSTEAD OF triggers on views to define custom INSERT, UPDATE and DELETE behavior.

## **7. WITH CHECK OPTION**

Very important for interviews!

It ensures INSERT or UPDATE through a view does not create a row that violates the view's WHERE condition.

Example:

```
CREATE VIEW it_employees AS
SELECT *
FROM employees
WHERE department = 'IT'
WITH CHECK OPTION;
```

Now:

```
INSERT INTO it_employees
VALUES (20, 'Priya', 'HR');
```



Error

&#x20;HR does not satisfy the view condition.



But:

```
INSERT INTO it_employees
VALUES (21, 'Rahul', 'IT');
```

Allowed

Without `WITH CHECK OPTION`, an insert or update through an updatable view could make a row disappear from that view because it no longer matches its filter.

## **8. Types of Views**

There are two important types in PostgreSQL.

### **A. Normal View**

```
CREATE VIEW employee_view AS
SELECT * FROM employees;
```

- Stores the query definition, not the result rows.
- Reads current underlying table data when queried.
- Does not normally store a separate copy of the data.

### **B. Materialized View**

A Materialized View stores the result of the query physically.

```
CREATE MATERIALIZED VIEW sales_summary AS
SELECT
    product_id,
    SUM(quantity) AS total_quantity
FROM sales
GROUP BY product_id;
```

Read it:

```
SELECT * FROM sales_summary;
```

Refresh it when the underlying data changes:

```
REFRESH MATERIALIZED VIEW sales_summary;
```

Interview important

**Normal View vs Materialized View**

| Normal View                   | Materialized View            |
| ----------------------------- | ---------------------------- |
| Stores query definition       | Stores query result          |
| Reads current underlying data | Shows data from last refresh |
| No separate result storage    | Uses storage                 |
| No refresh required           | Refresh required             |
| Usually less storage          | Requires more storage        |
| Useful for reusable queries   | Useful for expensive reports |

**Trick:** Normal View = Live query. Materialized View = Stored result that needs refreshing.

## **9. Advanced View concepts**

### **A. Materialized View – CONCURRENTLY**

Normally:

```
REFRESH MATERIALIZED VIEW sales_summary;
```

This can block readers while refreshing.

To refresh without blocking concurrent SELECT queries:

```
REFRESH MATERIALIZED VIEW CONCURRENTLY sales_summary;
```

Requirements:

- The Materialized View must already be populated.
- It must have a suitable UNIQUE index using ordinary columns (not a partial index or expression index).

Example:

```
CREATE UNIQUE INDEX idx_sales_product
ON sales_summary(product_id);
```

Now you can use `REFRESH ... CONCURRENTLY`.

### **B. Security in Views**

Views can help control which data users see.

Example:

```
CREATE VIEW public_employee_info AS
SELECT emp_id, name, department
FROM employees;
```

Users accessing this view need not be given access to every column through the view itself. However, permissions must be configured correctly.

PostgreSQL also supports:

- `security_invoker`: checks permissions using the user who queries the view.
- `security_barrier`: helps prevent certain filter-bypassing attacks involving functions with side effects or information leaks.

Example:

```
CREATE VIEW public_employee_info
WITH (security_invoker = true)
AS
SELECT emp_id, name
FROM employees;
```

These are advanced security features; simply creating a View does not automatically make your data secure.

### **C. Can we create an index on a normal View?**

No. You cannot directly create an index on a normal View.

```
CREATE INDEX idx_employee
ON employee_view(emp_id);
```

This does not work.

Instead, create an index on the original table:

```
CREATE INDEX idx_employee_id
ON employees(emp_id);
```

For a Materialized View, you can create indexes:

```
CREATE INDEX idx_sales_total
ON sales_summary(total_quantity);
```

### **D. Can one View use another View?**

Yes!

```
CREATE VIEW active_employees AS
SELECT *
FROM employees
WHERE status = 'active';
```

Now create another View:

```
CREATE VIEW it_active_employees AS
SELECT *
FROM active_employees
WHERE department = 'IT';
```

This is called a View based on another View.

Be careful with too many nested Views because they can make queries harder to understand and optimize.

## **10. How to see existing Views?**

List views in PostgreSQL using:

```
SELECT table_name
FROM information_schema.views
WHERE table_schema = 'public';
```

See the definition of a particular View:

```
SELECT view_definition
FROM information_schema.views
WHERE table_name = 'employee_view';
```

In pgAdmin, you can also find Views under:

`Database → Schemas → public → Views`

## **11. Common interview differences**

| Concept                   | Meaning                   |
| ------------------------- | ------------------------- |
| Table                     | Stores actual data        |
| View                      | Stores a query definition |
| Materialized View         | Stores query results      |
| CREATE VIEW               | Creates a View            |
| CREATE OR REPLACE VIEW    | Replaces its definition   |
| ALTER VIEW                | Changes View properties   |
| DROP VIEW                 | Removes a View            |
| REFRESH MATERIALIZED VIEW | Updates stored results    |

## **12. Common mistakes and tricks**

| Mistake                                  | Correct understanding                          |
| ---------------------------------------- | ---------------------------------------------- |
| Thinking View stores copied data         | Normal View stores query definition            |
| Thinking View is always updatable        | Only certain views are automatically updatable |
| Thinking UPDATE View updates a copy      | It updates underlying table data               |
| Forgetting to refresh materialized view  | It can show stale results                      |
| Creating an index on normal View         | Index the underlying table instead             |
| Thinking View automatically secures data | Configure permissions properly                 |
| Using DROP CASCADE carelessly            | It can remove dependent objects                |

## **13. Practical interview questions**

**Q1. What is a View?**

A virtual table created using a SELECT query.

**Q2. Why use a View?**

For query reusability, simplicity, reporting and controlled data access.

**Q3. Does a View store data?**

A normal View does not store a separate result set. A Materialized View does.

**Q4. Can we update a View?**

Yes, if it is automatically updatable or has suitable triggers.

**Q5. Difference between View and Materialized View?**

A normal View runs its query when accessed. A Materialized View stores results and needs refreshing.

**Q6. Can we create a View using JOIN?**

Yes.

**Q7. Can we create a View using GROUP BY?**

Yes, but such a View is generally not automatically updatable.

**Q8. What is WITH CHECK OPTION?**

It prevents INSERT or UPDATE through a View from creating rows that do not satisfy its WHERE condition.

**Q9. Can we create an index on a View?**

Not on a normal View. You can index its underlying tables or create an index on a Materialized View.

**Q10. What happens if the original table data changes?**

A normal View reflects the underlying data when queried. A Materialized View continues showing its stored result until refreshed.
